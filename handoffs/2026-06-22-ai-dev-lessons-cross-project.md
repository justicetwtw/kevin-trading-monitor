## 0. 怎麼用這份

- 開發 / 改 AI 相關功能前,先掃一次 §1–§7 的**粗體結論**。
- 改 `gooaye-digest` 或任何新 LLM 功能時,§8 的對照表 + §9 的 pre-flight checklist 逐條過。
- 這份是「判斷紀律」不是「步驟手冊」;遇到衝突以「量測勝過臆測」為最高仲裁。

## 1. 最高原則（三條,先記這個）

1. **先量測再下結論,別猜根因。** 出錯時不要先假設「是我的 code bug」也不要先甩鍋「模型爛」——**做一個能重現的最小實驗,用真實資料打 live,看數字**。實例:有個「人數被讀成 8」的 bug,使用者合理懷疑程式把 `4+4=8`;沒有臆測,直接打 live API 證明「程式沒有任何加總,是低解析又側放讓模型把手寫 4 看成 8」。**根因要有證據,不是有故事。**
2. **「合併了」≠「上線了」≠「使用者看得到」。** 三者之間有部署延遲與快取。每個改動要追到:部署 workflow 綠 → 打 live 端點驗行為 → 確認客戶端拿到新版。
3. **不拿準度換速度/成本,除非量測過沒退步。** 任何「壓縮、降解析、換小模型、量化、快取」都可能讓**難的案例**悄悄變差。優化後一定重測**難案**,留安全餘裕,且能快速 rollback。

## 2. 與 LLM / VLM 協作的紀律（最重要,最可轉移）

> 投資模型若用 LLM 解析財報/法說/新聞、做分類或抽取,以下全部適用。

- **一個 prompt 只做一件事(可靠度的第一槓桿)。** 雷:讓同一支 prompt「同時」辨識內容 + 判斷方向,模型會邊辨識邊腦補方向 → 極不穩;拆成獨立「只判方向」呼叫後,16/16 穩。**紀律:抽取、分類、判斷、計數不要塞同一次呼叫。** 投資對應:別讓同一 prompt 同時「抽財報數字 + 算 YoY + 給建議」,拆開、衍生值用 code 算。
- **問「具體的觀察」,把「抽象的判斷」留給程式算。** 雷:問「這圖轉了幾度」不穩;改問「標題列在上/下/左/右」(可在圖上指認)就穩,角度由 code 換算。**紀律:讓模型回報它能在輸入上「指出來」的東西,抽象結論用規則推導。** 投資對應:與其問「這公司健康嗎」,不如抽「流動比/負債比/現金流」,健不健康用你的規則判。
- **精準定義「不確定」的語意,別讓模型把「沒有」當「不確定」。** 雷:把**空白格**標成低信心 → 83 格假性「待補」。修法:prompt 明分三類——空白沒筆跡=高信心它是空的、有筆跡認不出=低信心、看得清=高信心填值。**紀律:凡會 gating 後續動作的「信心/旗標」,先把語意定義死。** 投資對應:「資料缺漏」vs「資料為 0」vs「模型沒把握」是三件事,別混。
- **輸入品質/解析度/上下文是準度的第一槓桿,勝過調 prompt。** 雷:整張多表報表壓到 1568px 後每格太小 → 漏讀、串行;裁出每張表用全解析度各自辨識後大幅改善。**紀律:先給模型「最大、最乾淨、只含相關區域」的視野,再談 prompt。** 投資對應:餵整份 100 頁 10-K 不如先定位到「合併損益表那一頁」再抽。
- **VLM 會「自我正規化」、有系統性盲點 → 實測畫出可靠軸,繞著它設計。** 雷:模型上下分得準、左右(直向文字)會混;且「從不把正的誤判成歪的」(無 false-positive)、只會「該轉的偶爾說沒轉」(false-negative)。利用錯誤不對稱性只信可靠軸 + 非零優先投票吃掉漏判。**紀律:實測模型的錯誤型態(哪種輸入穩、哪種飄、錯誤是否對稱),把決策建在它「可靠訊號 + 錯誤不對稱性」上。** 投資對應:LLM 對「方向性(利多/利空)」可能比「精確數字」可靠 → 讓它出方向、數字走結構化抽取。
- **投票/集成只救「隨機抖動」,救不了「系統性能力不足」。** 雷:1568px 偶爾飄一票 → 3 票投票救回(錯誤獨立);壓到 800px 時三票全錯(細節根本不夠)→ 投票無效。**紀律:多數決/重試只在錯誤彼此獨立時有效;若是輸入資訊量不足的系統性失敗,要補的是輸入(解析度/上下文),不是票數。**
- **降規格(小圖/小模型/量化)要實測門檻 + 留餘裕 + 重測難案。** 雷:為加速壓到 800px → 逆 90° 全錯;實測 1100px 才穩,用 1200px 留餘裕。**紀律:任何「便宜版本」掃出「仍 100% 正確的最小規格」,往上加一級當安全邊際,且只測簡單案沒用、要測最難的。**

## 3. 驗證紀律（量測 > 假設）

- **用真實、含邊角料的輸入測;別把「理想格式」寫死。** 雷:假設「兩表一定上下排」做垂直切;結果照片側放 90° 變左右並排 → 垂直切把兩表各砍一半。**紀律:列出你對輸入的隱含假設(方向、版面、欄位順序、單位、編碼),每條用真實髒資料打臉一次。** 投資對應:不同券商對帳單/不同年度財報版面會變,別假設欄位固定。
- **可疑數字先重現再修。** 做一個 10 行腳本打 live、印中間值,比讀三遍 code 快找到根因。
- **優化後先驗「沒退步」再合併。** 雷:800px 加速版在 merge 前就 live 實測發現準度掉,當場退回 1200px,沒污染 main。**紀律:效能/成本優化的 PR,合併前必跑準度回歸(尤其難案);準度是底線。**
- **「合併」不是終點,要驗到「線上行為」。** 雷:GAS/Worker/Pages 部署各有 30–90s 延遲與不同觸發;每次等部署綠 + 打 live 端點確認才算數。**紀律:知道每種改動觸發哪條部署管線、各自延遲;部署後打一次真實請求驗行為。** 偵測落地小技巧:打新端點回「unknown/404」=還沒上、回「正常/forbidden」=已上。

## 4. 部署 / 快取 / 相容性

- **客戶端有快取(SW/CDN/bundle)→ 每次前端改動必 bump 版本號。** 雷:後端改了輸出格式,PWA 停舊快取 → 畫面空白,看起來像 bug 其實沒拿到新前端。**紀律:改前端 = 改快取 VERSION;production「顯示舊值」第一步先驗 fresh-load(無快取)是否已正確。**
- **改 API 合約要「向後相容」撐過部署空窗。** 雷:後端從「單表」改「`sheets[]` 多表」,舊前端只讀頂層 → 空白;修法:後端同時保留頂層鏡像第一筆。**紀律:後端先佈、前端後佈的空窗期,新格式要 additive、保留舊欄位鏡像。** 投資對應:資料 schema/API 改版時,下游(回測、報表、前端)在部署那幾秒不能炸。
- **客戶端影像/資料處理有裝置上限,且常「無聲失敗」。** 雷:iOS Safari canvas 像素上限,裁切靜默失敗 → 退回更差路徑。**紀律:client 端重運算先查裝置上限;失敗路徑要 fail-safe(退回版本不能比原本爛)且可觀測。**
- **管線各自獨立,別把不相干的塞同一條。** 隔離分頁/審計快照別進主讀取路徑。**紀律:寫入目標、讀取來源、審計留痕分流清楚。**

## 5. 準度 vs 速度 / 成本

- **先畫依賴圖,並行所有「互不相依」的呼叫。** 雷:一張兩表照片序列跑 ~5 次呼叫;改成並行投票 + `Promise.all` 切塊後快約一半,準度不變。**紀律:模型單次延遲是地板;能並行的別序列。** 投資對應:多檔標的/多指標的 LLM 呼叫一律並行。
- **把貴的步驟用便宜的代理縮小。** 雷:方向偵測只需看版面 → 送小圖(但別過頭,見 §2 門檻)。**紀律:每個呼叫問「真的需要全解析度/全上下文嗎?」不需要就降規格(實測過的安全規格)。**
- **能跳過就跳過。** 雷:使用者已手動修正方向 → 跳過自動偵測,省一次呼叫。**紀律:有更可靠的上游資訊(人工/快取/前一步結果)時,別重複問模型。**

## 6. 產品 / 資料 / 態度

- **問題是結構化/確定的,就投資自動化,別過早把工作丟回使用者。** 雷:一度要使用者每張照片手動轉正,被打槍「固定格式不能讓 AI 自己判?」——他對的。**紀律:能用規則/模型可靠解的先自動化,手動只當 fallback。**
- **自動化也要留人工逃生口。** 自動方向偵測上線仍保留「手動旋轉鈕」。**紀律:auto + manual override 並存;加自動路徑別拆掉手動退路。**
- **自動決策要「預設動作 + 可逆」。** 雷:重複資料做成「預設跳過、但可一鍵『仍要送出』救回」,而非直接刪。**紀律:系統替使用者做的判斷(過濾/合併/跳過)要可一鍵還原且看得到。** 投資對應:模型自動「剔除異常值/略過某筆交易」也要可逆、可審。
- **「重複/相似」用內容相似度 + 可調門檻,不要只看主鍵。** 雷:同日期同組別不代表重複;比「值的集合相似度」(Jaccard 門檻 0.6)。**紀律:去重/比對用內容指紋 + 門檻,別只靠 id/日期硬比。**
- **Schema 先為「未來的查詢樣態」鋪好(additive)。** 雷:出勤只存「一列一次提交、名字擠逗號」不利未來 `GROUP BY 人`;先加「一人一列」明細表(additive)。**紀律:預期未來要 by-X 聚合,現在就存成 one-row-per-X;新增別改舊。** 投資對應:想之後做「個股/產業/因子」維度分析,落地就存到那個粒度。
- **PII / 敏感資料只進儲存,絕不進 log / 回傳 / telemetry。** 雷:姓名只寫 cell,回傳與 log 只給筆數。**紀律:敏感欄位(姓名、帳號、持倉、金額、API key)落 storage 可以,別落 log、別回傳給不需要的層。**

## 7. 工程節奏

- **小步快跑、每步 live 驗、敢退回。** 一次大改很難定位哪裡壞。**紀律:一個 PR 一個可獨立驗證的改動;先驗證假設(打 live)再蓋下一層。**
- **改之前先讀現場,別照「腦中印象/別人給的快照數字」硬改。** 對 live + 原始碼逐步推導,查不出就停下來問。
- **留下「自證」鉤子。** 關鍵邏輯(去重、契約相容、bootstrap)配一個能一鍵重跑的測試/端點,日後回歸一打就知道。

## 8. ⭐ 對應到本 repo:gooaye-digest + 交易監控

> 上面是通用教訓,這節是「在我們自己的 code 上具體長怎樣」。

### 8.1 gooaye-digest 已經做對的(對照踩雷,維持別退步)

| 教訓 | 本 repo 做法 |
|---|---|
| §2 一個 prompt 只做一件事 | 轉錄(`transcriber.py`)與摘要(`summarizer.py`)拆成**兩段獨立 Gemini 呼叫**,摘要吃純文字不吃音檔。**別為了省一次呼叫又合回去。** |
| §2 抽取 > 抽象判斷 | 摘要 prompt 要求「只根據逐字稿,不自行補充」,代號存疑標「(待確認)」——讓模型回報它逐字稿裡能指出來的,不腦補。 |
| §2 信心/不確定語意定義死 | 「(待確認)」= 辨識存疑,跟「逐字稿沒提到」是兩件事,prompt 已分開。 |
| §3 用真實髒資料測 + 隱含假設打臉 | `feed.py` 不假設 enclosure 一定是 audio/第一個;`_parse_duration` 吃 `HH:MM:SS` / `MM:SS` / 純秒三種;沒 guid/沒音檔的 item 跳過。 |
| §1 可疑先重現 | build 時實打 google-genai SDK 驗 `files.upload(file=,config=)` / `generate_content(model=,contents=,config=)` 簽章,不靠記憶。 |
| §6 自動但留逃生口 + 可逆 | bootstrap 首跑只處理最新 1 集、其餘標 seen(不灌 600 集);單集失敗**不標 seen**,下次自動重試(可逆)。 |
| §3 自證鉤子 | `tests/test_gooaye.py` 31 測試涵蓋 feed/dedup/bootstrap/email/pipeline,全 mock,回歸一打就知。 |
| §6 敏感資料不外洩 | API key / app password 走 GitHub Secrets,不寫死、不進 log。 |

### 8.2 gooaye-digest 的已知風險與待辦(對照踩雷,主動盯)

- **§1/§2 輸入品質 > prompt:長音檔單次轉錄可能被輸出 token 截斷或「漂移成摘要」。** 現況 v1 單次 + 強逐字 prompt + 大 `max_output_tokens`。**盯法:第一封信來時實際比對逐字稿尾段有沒有斷;斷了就走 §7.2 切段 fallback(已標 TODO)——這是「補輸入/切片」不是「加票數」(§2 投票救不了系統性不足)。**
- **§1.3 不拿準度換成本:未來想換更小/更便宜模型或降音質前,先拿一集難的(台味國語 + 俚語密集)實測,別只測乾淨段。** 模型 ID 已抽成 `GEMINI_MODEL` 一行可換 + rollback。
- **§4 部署 ≠ 上線:GitHub Actions 對低活動 repo 有 schedule throttle(本 repo 文件記過延後 2.5h / 漏觸發)。** gooaye `*/30` cron 多數 no-op,延遲可接受;真要硬化接 Cloudflare Worker 備援觸發。**驗收第一集時,別假設「cron 設了就會準時跑」,用 workflow_dispatch 手動驗。**
- **§4 相容/競態:seen 狀態靠 `commit-state` action `pull --rebase` 防 push race。** 改 seen 結構(目前 `guid → {seen_at,title}`)時要 additive,別讓正在跑的其他 workflow 撞爛 `data_store/`。
- **§3 合併 ≠ 使用者看得到:完成標準是「Kevin 真的收到一封信 + 再觸發不重寄」。** 真實寄信前先跟 Kevin 講會寄幾封(避免 bootstrap 誤灌)。
- **§5 並行:目前每集序列處理(每 run ≤2 集,夠用)。** 若未來放寬 `MAX_EPISODES_PER_RUN` 或加多 podcast,再考慮並行,別預先複雜化。

### 8.3 交易監控通用提醒(既有 code 已有紀律,別退步)

- **§2 抽取/衍生分離**:LLM 只做分類/抽取(如 `trump_classifier` / `news_classifier`),訊號分數一律 code 算,別讓模型直接吐「買賣建議」。
- **§3 fallback 紀律**:既有 yfinance / 雙源抓取都 try/except + 回空不阻塞(`trump_truth.py` 雙源、`_cold_start` 冷啟動保護),新功能比照,**單點失敗不炸整條 run**。
- **§6 schema additive**:universe / thresholds 改動走 additive,下游(scorer/回測/brief)在部署空窗不能炸。
- **§6 PII/部位**:金額、持倉、帳號落 storage 可以,別進 log / 推播 / telemetry。

## 9. 開工前 pre-flight checklist（新增/修改 AI 功能必過）

1. [ ] 這個改動是不是把多件事塞進一個 prompt?能拆就拆(§2)。
2. [ ] 我對輸入的隱含假設列出來了嗎?(格式、方向、欄位、單位、編碼、長度)每條用真實髒資料打臉過?(§3)
3. [ ] 會 gating 後續動作的旗標(信心、seen、待確認、缺漏)語意定義死了嗎?(§2)
4. [ ] 我用 live / 真實樣本量測過根因/行為,而不是讀 code 臆測?(§1)
5. [ ] 如果做了任何「便宜版本」(小模型/降規格/快取),掃過最小安全規格 + 重測**難案**了嗎?(§1.3 / §2)
6. [ ] 每個外部呼叫(網路/模型/寄信)都 try/except + fallback,單點失敗不炸整條 run?(§3)
7. [ ] 自動決策有「預設動作 + 可逆 + 看得到」?有人工逃生口?(§6)
8. [ ] 敏感資料(key / 持倉 / 金額)只進 storage,沒進 log / 回傳?(§6)
9. [ ] 改 schema / API 合約是 additive、撐得過部署空窗?(§4)
10. [ ] 留了可一鍵重跑的測試 / dump 當自證鉤子?(§3 / §7)
11. [ ] 驗收追到「使用者真的看得到新行為」,不是停在「PR merged」?(§1.2 / §3)

### 一句話總結

> **量測勝過臆測、輸入品質勝過 prompt 花招、拆任務勝過塞一支、自動化但留逃生口、優化不犧牲準度、合併不等於上線。**
